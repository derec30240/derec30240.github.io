本文完整记录一次在 WSL2 环境下用 USB 连接 Android 手机、运行 Flutter debug 模式的过程，包括最终方案、走过的弯路、犯过的错误、排查方法和经验总结。

最终状态：一条 ./scripts/run_android.sh 就能稳定构建、安装、启动并热重载。

说明 本文由 DeepSeek V4.1 Flash 1017 使用 OpenCode 撰写。人工仅参与配图与最后校对。

最近在 WSL2 里写 Flutter。写代码的时候岁月静好，一到真机调试就当场傻眼——WSL2 根本看不到 USB 设备。理论上 Windows 和 WSL2 是相亲相爱一家人，实际上 USB 设备表示：抱歉，我不认识路。

于是就有了这次横跨 USB 物理层、Windows 驱动、adb server、adb forward、VM Service、Gradle 网络六层的排查。最终方案是 Windows adb server + WSL TCP 中继，一条脚本搞定全流程。下面把答案和弯路一起摊开讲讲。

结论速览
#

先把答案放在前面，免得你陪我一起踩坑。

  • 项目：一个最小 Flutter 应用。
  • 设备：Xiaomi 17 Pro（型号 25098PN5AC，Android 17 / API 37，arm64-v8a）。
  • 最终方案：Windows adb server + WSL TCP 中继。
  • 一键入口：./scripts/run_android.sh。
  • 最终验证：构建成功、APK 安装成功、debug 启动、热重载成功；adb install 成功说明 USB 批量传输可用。
  • 走过的弯路：试过 usbipd-win，拓扑确实更简单，但本机 USB/IP 批量传输不稳定，最终卸载回退。

一句话总结：adb 的 5037 是控制通道，VM Service 的 8888 是数据通道。 前者通不代表后者通，后者通也不代表批量传输稳定。把这两条通道混为一谈，是本次一半弯路的总开关。

最终架构
#

┌──────────────────────────── WSL2 ────────────────────────────┐
│                                                              │
│  flutter run                                                 │
│    │                                                         │
│    ├─ adb 客户端 ── ADB_SERVER_SOCKET=tcp:<HOST_IP>:5037 ──┐ │
│    │                                                       │ │
│    └─ VM Service ── 127.0.0.1:8888 ── relay ──┐            │ │
│                                               │            │ │
└───────────────────────────────────────────────┼────────────┼─┘
                                                │            │
                                                ▼            ▼
                                      ┌──────────────────────────┐
                                      │ Windows                  │
                                      │  adb server 0.0.0.0:5037 │
                                      │  adb forward 0.0.0.0:8888│
                                      └────────────┬─────────────┘
                                                   │ USB
                                                   ▼
                                            ┌─────────────┐
                                            │ Android 手机 │
                                            │  adbd       │
                                            │  VM Service │
                                            └─────────────┘

这张图里有两个通道，必须分开理解：

  1. 控制通道：flutter 调用 adb 安装、启动、抓 logcat、建 forward，走的是 Windows adb server 的 5037。
  2. 数据通道：VM Service 的端口转发创建在 Windows 上，WSL 里的 flutter 需要本地中继才能访问。

很多「连不上」的问题，本质都是把这两个通道混为一谈——就像把「能打电话」当成「能见面」。

排查过程
#

第一步：WSL2 根本看不到 USB 设备
#

现象很干脆：

adb devices        # 空列表
ls /dev/bus/usb    # No such file or directory

adb devices 空空如也，那个空列表仿佛在无声地嘲笑我。

原因不复杂：WSL2 默认不会把 Windows 的 USB 设备透传进来，而 Windows 侧也没有装 usbipd-win。不过在 Windows 侧，手机倒是活得好好的：

ADB Interface
Xiaomi 17 Pro    USB\VID_2717&PID_FF48

方案对比下来有三种：

方案结果
无线调试 adb tcpip 5555手机监听 *:5555，但 WSL/Windows 均无法稳定连到手机 LAN IP，放弃
usbipd-win 透传 USB 到 WSL可 attach，但 USB/IP 批量传输不稳定，最终放弃
Windows adb server + WSL TCP 连接最终采用，稳定可用

第二步：把 adb server 放到 Windows 上
#

系统里没有现成的 adb.exe，而 dl.google.com 又不可达。于是用腾讯镜像下载 Windows 版 platform-tools：

curl -o /tmp/platform-tools-win.zip \
  https://mirrors.cloud.tencent.com/AndroidSDK/platform-tools-latest-windows.zip
unzip -q /tmp/platform-tools-win.zip -d /mnt/c/Users/Dexter/AppData/Local/Android/

然后在 Windows 启动 adb server，并监听所有网卡：

Start-Process -FilePath 'C:\Users\Dexter\AppData\Local\Android\platform-tools\adb.exe' `
  -ArgumentList '-a','nodaemon','server' -WindowStyle Hidden

验证一下，看看它到底认不认人：

adb.exe devices -l
# 34dfc28a  device  product:pandora model:25098PN5AC ...

WSL 通过宿主机网关访问这个 adb server：

export ADB_SERVER_SOCKET=tcp:172.29.112.1:5037
adb devices -l

172.29.112.1 是 WSL2 的默认网关（Windows vEthernet 地址），WSL 重启后可能变化。项目脚本会自动从 ip route 读取，不必手写死——毕竟每次重启都改一遍，人会疯的。

第三步：处理 unauthorized 和 offline
#

  • 首次连接显示 unauthorized：解锁手机，点「允许 USB 调试」，可以勾选「始终允许」。这感觉就像手机在礼貌地问你：「我凭什么相信你？」
  • 出现 offline 时，按顺序尝试：
    • 解锁手机；
    • 重新插拔数据线；
    • 必要时撤销 USB 调试授权后重新授权；
    • 必要时重启手机；
    • 重启 Windows adb server。

offline 这玩意儿很像失联的前任——你发什么都已读不回。也试过 adb tcpip 5555，但手机 LAN IP 从 WSL/Windows 都不稳定可达，反而增加变量，果断放弃。

为了减少锁屏导致调试中断：

adb -s 34dfc28a shell svc power stayon usb

第四步：VM Service 连不上
#

第一次 flutter run 已经成功安装并启动 App，但连接 VM Service 失败：

Exception attempting to connect to the VM Service:
SocketException: Connection refused ... address = 127.0.0.1, port = 50532

原因很典型：

  • adb forward tcp:50532 ... 是在 Windows adb server 上创建的，端口监听在 Windows。
  • WSL 里的 flutter 连接 127.0.0.1:50532 时，访问的是 WSL 自己的 loopback，自然被拒。

这就像你照着邻居家的地址去敲门，敲开的却是自己家的门——人当然不在。

解决办法是固定端口 + 本地中继：

  1. 使用 --no-dds --host-vmservice-port=8888。

  2. 在 Windows 侧创建占位转发：

    ADB_SERVER_SOCKET=tcp:172.29.112.1:5037 \
  adb -s 34dfc28a forward tcp:8888 tcp:5555

  3. 在 WSL 启动中继：127.0.0.1:8888 -> 172.29.112.1:8888。

  4. Flutter 会把 tcp:8888 更新到真实的 VM Service 设备端口。

这里有个关键点：默认开启 DDS 时，--host-vmservice-port 会被当作 DDS 端口，VM Service 仍然使用随机端口。所以要么加 --no-dds，要么同时显式指定 --dds-port。不然就是「端口设了，但没完全设」。

第五步：端口冲突
#

中继和转发都建好之后，又撞上了端口占用：

adb: error: cannot bind listener:
cannot bind to 0.0.0.0:8888: 通常每个套接字地址只允许使用一次 (10048)

原因是 WSL 监听 127.0.0.1:8888 时，WSL2 的 localhost forwarding 会把它镜像到 Windows，导致 Windows adb 无法再绑定同一端口。

一个 8888，两个人都想要。WSL2 的 localhost forwarding 摊摊手：我先到先得。

解决靠调整启动顺序：

  1. 先创建 Windows 占位转发；
  2. 再启动 WSL relay。

顺序反了就会冲突。项目脚本已按正确顺序处理，并在创建转发前先停掉旧 relay。

第六步：连接约 1 秒后掉线
#

这是最迷惑人的一个问题：

A Dart VM Service ... is available at: http://127.0.0.1:8888/xxx=/
Service protocol connection closed.
Lost connection to device.

此时 adb devices 正常、App 进程仍存活，说明不是 USB 掉线，而是 VM Service 的 WebSocket 被中继关闭了。

我在那儿反复插拔数据线的时候，数据线一定很委屈：这锅我不背。

根因在 relay 里的一行代码：

socket.create_connection(TARGET, timeout=1)

这个超时会一直作用到后续的 recv。WebSocket 空闲超过 1 秒就触发 socket.timeout，中继随即关闭连接。timeout=1 这短短几个字符，害我怀疑了半天硬件，属实冤枉。

修复方法：

upstream = socket.create_connection(TARGET, timeout=1)
upstream.settimeout(None)  # 建连超时只用于建连，之后恢复阻塞

验证时用 Python 手动完成 WebSocket 握手，每秒发送一次 getVM，连接可以持续 8 秒以上。稳了。

第七步：Gradle 构建几十分钟没进度
#

这个坑看起来像编译在憋大招，其实是网络挂起：

  • flutter run 卡在 Running Gradle task 'assembleDebug'...；
  • 构建目录几分钟没有新文件；
  • ss 显示 Java 进程在等 storage.googleapis.com:443。

你以为是 CPU 在燃烧，其实是 Java 进程站在 Google 门口排队，望眼欲穿。

根因是启动脚本里执行了 unset FLUTTER_STORAGE_BASE_URL，Flutter Gradle 插件于是重新去连 Google 源。

修复分两步。首先把 Flutter 存储镜像放到 Gradle 仓库第一项：

maven("https://storage.flutter-io.cn/download.flutter.io")
maven("https://maven.aliyun.com/repository/google")
maven("https://maven.aliyun.com/repository/public")
maven("https://mirrors.cloud.tencent.com/nexus/repository/maven-public/")
google()
mavenCentral()

然后增加网络超时，避免单个请求卡很久：

systemProp.org.gradle.internal.http.connectionTimeout=15000
systemProp.org.gradle.internal.http.socketTimeout=15000

顺便记录一下构建耗时，心里有个底：

  • 冷启动 / Gradle daemon 被杀后首次构建：约 97 秒；
  • 紧接着的增量构建：约 3–5 秒；
  • 热重载：约 100–300 毫秒。

结论是：日常构建慢先查网络，不要先怀疑编译。 flutter clean 和杀死 Gradle daemon 都会让下一次构建重新变慢。这就像每次出门前都把冰箱清空再重新采购——除了累，没有任何好处。

第八步：usbipd-win 的弯路
#

既然 Windows adb server 这么绕，那能不能让 WSL 直接看到 USB，省掉中间商赚差价？这个念头很诱人，于是尝试了 usbipd-win。

安装、绑定、附加：

winget install --interactive --exact dorssel.usbipd-win
usbipd list
usbipd bind --force --busid 2-2
usbipd attach --wsl --busid 2-2

结果问题一个接一个，堪称「按下葫芦浮起瓢」。

  1. attach 后立即断开

    vhci_hcd: Device attached
vhci_hcd: connection closed
    • 原因一：usbipd 服务状态异常，Restart-Service usbipd 后可恢复。
    • 原因二：usbipd-win 5.3.0 对部分 Android 设备存在回归（GitHub issue #1336），降级到 4.2.0 后 attach 恢复。

  2. 连接 2–3 分钟后空闲断开

    • 检查发现 USB 选择性暂停处于开启状态（AC/DC 都是 0x1）。
    • 两个 USB Root Hub 都允许「关闭此设备以节省电源」。
    • ADB 空闲时端口被挂起，vhci_hcd 报 connection closed。

    关闭方法（管理员权限）：

    powercfg /setacvalueindex SCHEME_CURRENT 2a737441-1930-4402-8d77-b2bebba308a3 48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
powercfg /setdcvalueindex SCHEME_CURRENT 2a737441-1930-4402-8d77-b2bebba308a3 48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
powercfg /setactive SCHEME_CURRENT
Get-CimInstance -Namespace root\wmi -ClassName MSPower_DeviceEnable |
  Where-Object { $_.InstanceName -like 'USB\ROOT_HUB*' } |
  ForEach-Object { $_.Enable = $false; Set-CimInstance -InputObject $_ }

    关闭后，空闲断开问题解决。

  3. 真正致命的问题：USB/IP 批量传输不稳定

    • adb shell 正常，但 adb push 5MB 文件：

      adb: error: failed to read copy response: EOF
1 file pushed ... (5MB in 8.6s)

    • 随后设备从 adb 消失，dmesg 出现：

      vhci_hcd: urb->status -104

    • adb install 也会卡住，flutter run 报：

      Error: ADB exited with exit code 1
adb: failed to install ...
Error launching application ...

    这是 USB/IP 批量传输与当前手机/主机的兼容性问题，不是单纯的电源管理能救回来的。用一句话形容就是：握手没问题，一搬重物当场表演「我裂开了」。

最终处理：

  • 卸载 usbipd-win：

    winget uninstall --id dorssel.usbipd-win --silent

  • 恢复 Windows 直接管理 USB；

  • 回到 Windows adb server + TCP 中继方案；

  • 保留关闭 USB 节能的设置（对 USB 稳定性有帮助）。

第九步：后台运行的 flutter run 没有交互
#

flutter run 的 r/R/q 依赖 stdin。用 setsid 后台启动且 stdin 为 /dev/null 时，可以启动，但无法热重载，行为也不稳定，甚至可能提前退出。

解决办法是用命名管道作为 stdin，并保持写端常开：

mkfifo /tmp/opencode/flutter_in
setsid -f bash -c 'exec 3>/tmp/opencode/flutter_in; sleep infinity' </dev/null

setsid -f bash -c \
  'exec flutter run -d 34dfc28a --debug --no-dds --host-vmservice-port=8888 \
   < /tmp/opencode/flutter_in > /tmp/opencode/flutter_run.log 2>&1' </dev/null

之后热重载就是：

printf 'r\n' > /tmp/opencode/flutter_in

正常在终端里运行时不需要 FIFO，直接按键即可。别为了「优雅地后台运行」把自己绕进管道里。

第十步：封装成一键脚本
#

为了避免每次手工重复「启动 adb server → 找设备 → 建转发 → 启动 relay → flutter run」，最终封装成：

./scripts/run_android.sh

脚本流程固定为：

  1. 启动 Windows adb server，监听 0.0.0.0:5037；
  2. 通过 ADB_SERVER_SOCKET 检测已授权设备；
  3. 停止旧 relay；
  4. 创建占位转发 tcp:8888 -> tcp:5555；
  5. 启动 WSL relay 127.0.0.1:8888 -> <HOST_IP>:8888；
  6. 执行 flutter run --debug --no-dds --host-vmservice-port=8888；
  7. 退出时清理 relay。

人类的本质是复读机，而脚本是更好的复读机。顺序固定下来之后，人为出错的概率就小多了。

犯过的错误与教训
#

回头看，这次排查真正的价值不在「怎么修好」，而在「为什么一开始修错了」。

把 Lost connection 直接当成 USB 掉线
#

现象是 Lost connection to device，实际 adb devices 正常、App 也活着，真正原因是 relay 的 1 秒 socket 超时。

教训：日志关键词不等于根因。 先分别验证设备、adb、进程、VM Service 是否存活，再下结论。不然就会像我一样，对着无辜的数据线反复施法。

先启动 relay，再创建 adb forward
#

现象是 cannot bind to 0.0.0.0:8888。因为 WSL localhost forwarding 把 WSL 的 8888 镜像到了 Windows，Windows adb 就无法再绑定。

教训：跨 WSL/Windows 的端口有明确的「所有者」。 顺序必须是先 Windows forward，再 WSL relay。

relay 使用持久的 socket 超时
#

短请求正常，WebSocket 约 1 秒断开。原因就是 create_connection(timeout=1) 的 timeout 延续到了 recv。

教训：连接超时只用于建连，之后必须 settimeout(None)。

依赖环境变量，却在启动时 unset
#

Gradle 卡在 storage.googleapis.com 几十分钟，因为启动命令里 unset FLUTTER_STORAGE_BASE_URL，Flutter 插件又去连 Google。

教训：关键镜像配置写进项目 Gradle 配置，不要依赖临时环境变量。 环境变量这玩意儿，说没就没。

把冷构建当成「每次构建都慢」
#

一次构建 97 秒，很容易误以为每次都要这么久。实际冷启动 97 秒，增量构建只要 3–5 秒。

教训：区分冷构建、增量构建、热重载；不要频繁 flutter clean 或杀 Gradle daemon。

过早相信「usbipd 更简单」
#

拓扑确实更简单，但 adb push / adb install 批量传输失败。

教训：用真实工作负载验证链路。 adb shell 能用不代表 APK 能装；这就像能打招呼，不代表能一起过日子。必须测试 adb push、adb install 和 flutter run 全链路。

usbipd bind 没有加 --force
#

attach 后 Windows 驱动可能重新占用设备，连接不稳定。

教训：usbipd bind --force 让宿主彻底释放设备；回退时要 unbind 或卸载，否则持久绑定会让 Windows adb 看不到手机。

忽略 USB 节能
#

手机亮屏，但空闲 2–3 分钟后断开，根子是 USB 选择性暂停 + Root Hub 电源管理。

教训：手机亮屏 ≠ USB 链路不会省电。 屏幕亮着只是它在营业，不代表 USB 不打瞌睡。

设备 offline 时反复执行 adb 命令
#

offline、device not found 反复出现时，正确顺序是：

  • 先看 Windows 设备管理器 / PnP 是否还有 ADB Interface；
  • 解锁手机、重插数据线、撤销并重新授权；
  • 必要时重启手机；
  • 再重启 adb server。

教训：adb 层反复重试解决不了物理层和授权层的问题。 你对着一个没开门的屋子狂按门铃，门铃也很无奈。

后台运行 flutter run 时使用 /dev/null 作为 stdin
#

进程能启动，但无法热重载，行为不稳定。

教训：需要后台运行时用 FIFO + 常开写端；正常调试直接在终端运行。

pkill -f 匹配到当前 shell
#

执行 pkill -f "relay.py" 时，当前 bash 命令行也包含这个字符串，结果把自己杀掉了。

教训：用更精确的 pattern，或先 pgrep 得到 PID 再 kill。 别让清理脚本顺手把你本人也清理了。

验证清单
#

排查到最后，判断「到底修好了没有」比记住修复命令更重要：

  • adb devices -l 显示 device
  • adb shell echo OK 正常
  • adb push 一个 5MB 文件成功（验证批量传输）
  • adb install -r app-debug.apk 成功（验证 APK 安装）
  • flutter devices 能看到手机
  • ./scripts/run_android.sh 能完成构建、安装、启动
  • 日志出现 Dart VM Service ... is available
  • 热重载成功（Reloaded ...）
  • 手机长时间空闲后连接不中断

其中 adb push 和 adb install 是区分「能连上」和「能调试」的关键。别被 adb shell 的一句 OK 骗了，那只是社交辞令。

经验总结
#

  1. 先分层，再定位。 这次问题跨了 USB 物理层、Windows 驱动、adb server、adb forward、VM Service、Gradle 网络六层。每层都用最小命令验证，比反复重装、重启有效得多。

  2. 控制通道与数据通道分开看。 adb 的 5037 是控制通道，VM Service 的 8888 是数据通道。前者通不代表后者通；后者通也不代表批量传输稳定。

  3. 跨 WSL/Windows 时，端口有明确「所有者」。 adb forward 创建在 Windows，WSL 的 127.0.0.1 是另一个 loopback，必须有显式中继。别指望它自己长腿跑过来。

  4. 代理长连接必须清除建连超时。 create_connection(timeout=1) 会影响后续 recv；短请求测不出问题，WebSocket 会很快断开。

  5. 镜像配置要写进项目，不要依赖临时环境变量。 把 storage.flutter-io.cn 放到 Gradle 仓库首位，并设置 HTTP 超时，一次配置，长期受益。

  6. 用真实工作负载验证链路。 adb shell、lsusb 只能证明「连上了」。adb push 和 adb install 才能证明「能调试」。

  7. 「更简单」不等于「更可靠」。 usbipd 拓扑更简单，但本机批量传输失败。选型时必须跑完整链路，而不是只看 attach 成功。中间商少，不代表货能送到。

  8. 冷构建和增量构建要分开评价。 冷启动 97 秒是正常的；增量构建 3–5 秒才是日常体验。不要因为一次冷启动就频繁 clean。

  9. 先查物理层和授权，再查软件层。 offline、设备消失、安装失败，很多是线材、接口、锁屏、授权、手机 USB gadget 状态导致的，重启、重插、重新授权往往比反复敲 adb 命令有效。

  10. 回退要彻底。 usbipd 的持久绑定和驱动会影响 Windows adb。决定放弃时，要 unbind 或卸载，并确认 Windows 重新接管设备。

  11. 把重复操作脚本化。 手工步骤越多，越容易顺序出错（尤其是 forward 与 relay 的顺序）。脚本把顺序固定下来，减少人为错误。

  12. 记录现象、命令、根因和验证方式。 只记录「怎么修」不够，还要记录「怎么确认修好了」。这份验证清单和速查表就是为此保留的。

import os
import socket
import threading
import time

LISTEN_HOST = os.environ.get("RELAY_LISTEN_HOST", "127.0.0.1")
LISTEN_PORT = int(os.environ.get("RELAY_LISTEN_PORT", "8888"))
TARGET_HOST = os.environ["RELAY_TARGET_HOST"]
TARGET_PORT = int(os.environ.get("RELAY_TARGET_PORT", "8888"))


def pipe(src, dst):
    try:
        while True:
            data = src.recv(65536)
            if not data:
                break
            dst.sendall(data)
    except Exception:
        pass
    finally:
        try:
            dst.shutdown(socket.SHUT_WR)
        except Exception:
            pass


def handle(client):
    upstream = None
    for _ in range(50):
        try:
            upstream = socket.create_connection((TARGET_HOST, TARGET_PORT), timeout=1)
            upstream.settimeout(None)  # 关键：建连后恢复阻塞
            break
        except Exception:
            time.sleep(0.2)
    if upstream is None:
        client.close()
        return
    threading.Thread(target=pipe, args=(client, upstream), daemon=True).start()
    pipe(upstream, client)


server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind((LISTEN_HOST, LISTEN_PORT))
server.listen(64)
while True:
    client, _ = server.accept()
    threading.Thread(target=handle, args=(client,), daemon=True).start()
